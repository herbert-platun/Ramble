Überblick

Das Gesamtbild: Wer entscheidet was, und wann?

Architektur: Der Server entscheidet, die Geräte spielen ab

handler.py, app.py

Die gesamte Spiellogik läuft auf dem Server, auch Zufall, Abrechnung und das Timing jeder Animation. Die Geräte bekommen per Server-Sent Events einen Zustand mit Zeitstempeln und berechnen jedes Bild daraus. Kein Client trifft eine Entscheidung.

Ablauf einer Ziehung

game/draws.py

Jede Ziehung hat vier Zeitpunkte in Server-Millisekunden. Das ganze System baut auf ihnen auf:

pick()Topf einfrieren. Der Gewinner steht noch nicht fest.
locks_at„Nichts geht mehr“: ziehen und abrechnen.
started_atDie Animation startet (+1.700 ms).
ends_atErgebnis sichtbar. Beim Rad sind es 9,5 s Drehung.

Die Einsatzphase dauert 7 s, bei Slots 10 s. Sie gibt es nur, wenn mindestens ein Handy mitspielt. Ohne Handys wird sofort gezogen.

Fairness & Zufall

Zufall muss ehrlich sein. Er darf nicht vorzeitig durchsickern und muss trotzdem genau dort landen, wo der Server gezogen hat.

Spätes Ziehen

draws.py, settle()

Der Gewinner wird erst bei locks_at gezogen. Dann sind keine Tipps und Einsätze mehr möglich, und alle Namen im Topf haben exakt dieselbe Chance.

winner_id = secrets.choice(slots)        # kryptografischer Zufall
slot      = slots.index(winner_id)
# Tipp-Treffer: +200 Chips, alles in einer Transaktion

settle() ist idempotent: Es sucht nur nach noch nicht abgerechneten Ziehungen. Ein zweiter Aufruf ändert also nichts.

Warum:Bis locks_at existiert der Name nirgends, auch nicht im Netzwerkverkehr. Wer den Datenverkehr mitschneidet, erfährt nichts.

Verzögerte Sichtbarkeit (Rückrechnung)

app.py, public()

Abgerechnet wird sofort, die Anzeige soll das Ergebnis aber erst zum Ende der Animation zeigen. Deshalb rechnet public() den Zustand für jede Auslieferung zurück, solange t < ends_at:

für jede abgerechnete, noch laufende Runde:
    chips[b] −= gewinn[b]
    wetten[b] = einsätze_vor_der_runde[b]

Bis zum Ergebnis enthält die Ziehung im Layout nur die Namen, aber nicht den Weg der Plinko-Kugel und nicht den Gewinner.

Plinko-Brettform

game/plinko.py

Bei wenigen Namen werden die Fächer breiter, bei vielen Namen kommen Reihen dazu:

per  = ⌈8 / n⌉                              Spalten je Name
rows = clamp(round(n · per · 0,6) + 4, 8, 16)
rows = rows − (rows mod 2)                   immer gerade

Jede Reihe verschiebt die Kugel um ±½ Spalte. Nach einer ungeraden Zahl von Reihen stünde sie also auf einer halben Position zwischen zwei Fächern. Die gerade Reihenzahl schließt das aus.

Plinko-Zufallspfad mit Erreichbarkeits-Bedingung

plinko.py, plinko_path()

Der Weg soll zufällig wirken und trotzdem garantiert im gezogenen Fach enden. Darum wird er Schritt für Schritt erzeugt, aber nur aus Schritten, nach denen das Ziel noch erreichbar ist:

ziel  = fach · per + randbelow(per)
start ∈ { c : |c − ziel| ≤ rows/2 }                 zufällig
für übrig = rows … 1:
    optionen = { d ∈ {−½, +½} : im Brett  ∧  |ziel − (pos+d)| ≤ (übrig−1)/2 }
    pos += choice(optionen)
assert pos == ziel

Kniff:Es braucht kein Verwerfen und keine Neuversuche: Jeder Schritt ist zulässig, und das Ende ist garantiert. Die Einschränkung wirkt erst gegen Ende, deshalb sieht die Bahn natürlich aus.

Deterministischer Landepunkt des Rads

stages/stage.js, hashRand()

Das Rad soll nicht immer genau in der Feldmitte stehen bleiben. Trotzdem müssen alle Geräte dieselbe Stelle zeigen. Die Abweichung wird deshalb aus einem Hash der Ziehungs-ID berechnet und nicht übertragen:

x = (id · 2654435761) >>> 0          Knuth-Multiplikation
x ^= x >>> 15;  x = imul(x, 2246822519);  x ^= x >>> 13
jitter = x / 2³² − 0,5
ziel   = −(slot + 0,5 + 0,7 · jitter) · seg      (±35 % eines Feldes)
ende   = ziel + k · 2π,   k so, dass mindestens 7 volle Umdrehungen

Statistische Fairness-Tests

tests/test_game.py

Die Gleichverteilung wird nicht nur behauptet, sondern bei jedem Build geprüft. Die Grenzen sind so gewählt, dass ein fairer Zufall sie praktisch nie verletzt, eine grobe Verzerrung aber sofort auffällt:

test_fair         3 Namen, 900 Ziehungen     erwartet 300 je Name
                  σ = √(900 · ⅓ · ⅔) ≈ 14,1   Grenze 220–380  (±5,7 σ)
test_slots_fair   3 Namen, 600 Sessions       erwartet 200 je Name
                  σ = √(600 · ⅓ · ⅔) ≈ 11,5   Grenze 140–260  (±5,2 σ)
test_deterministic_and_paying
                  gleicher Seed → identische Runde
                  3.000 Spins, 100 Chips auf 1 von 5 Namen
                  Auszahlung / Einsatz ∈ [0,75; 1,2]   (Soll 0,96)

Dazu kommen Tests, die für viele Zielfächer prüfen, ob der Plinko-Pfad wirklich dort endet, und ob die Kugel einer echten Ziehung im Fach des Gewinners landet.

Die Slot-Engine

Ein 5×3-Automat, in dem jeder Name ein Symbol ist. Alles ist eine reine Funktion des übergebenen Zufallsgenerators: SystemRandom im Spiel, ein fester Seed in Tests und bei der Kalibrierung.

Zellgewichte

game/slots.py, roll_grid()

Jede der 15 Zellen wird einzeln gewürfelt:

ZelleWirkungAnteil
Joker Wersetzt jeden Namen in einem Muster4,5 %
Niete Nblockiert; ab drei Nieten ist der Spin „Pleite“5,0 %
Faktor ×2/×3/×5Gewicht 70 : 24 : 6, multipliziert den ganzen Spin4,0 %
Namealle Namen gleich wahrscheinlich86,5 %

Klebrige Walzen

slots.py, stickiness()

Auf echten Walzenstreifen sind Symbole gestapelt. Das bildet das Spiel nach: Eine Namenszelle übernimmt mit Wahrscheinlichkeit h ihren linken und mit 0,55·h ihren oberen Nachbarn. Je mehr Namen am Tisch sind, desto stärker kleben sie:

h(n) = max(0, 0,42 · (1 − e^(−(n − 2,5) / 2)))

Warum:Ohne diesen Effekt gäbe es an Tischen mit 30 Namen fast nie drei gleiche Symbole nebeneinander. Weil die Klebrigkeit für alle Namen gleich wirkt, bleibt die Chance für jeden gleich.

Glücks-Spin als Wachstumsprozess

slots.py, apply_luck()

Bei 20 % der Spins wächst ein Name, der im Bild steht, wie bei einem schrittweisen Flood-Fill:

ziel = choice(namen im bild);   k = randint(3, 5)
k-mal:
    rand = orthogonale Nachbarn aller ziel-Zellen − eigene Zellen
    rand = rand ohne Joker und Faktoren          (die bleiben stehen)
    eine zufällige Randzelle → ziel

Die Walzen halten am Bild vor dem Glück an. Danach wird jede Umwandlung einzeln animiert (720 ms).

Waagerechte Läufe mit Jokern

slots.py, find_patterns()

Für jede Reihe und jeden Namen darin wird der längste zusammenhängende Lauf aus eigenen Zellen und Jokern gesucht:

für jede reihe, für jeden namen darin:
    scanne links → rechts; zelle ∈ {name, W} verlängert den lauf
    lauf ≥ 3 ∧ mindestens eine echte namenszelle  →  row3 / row4 / row5

Ein Joker kann so zu den Läufen mehrerer Namen gehören. Doppelte Treffer werden über den Schlüssel (besitzer, sortierte Zellen) entfernt.

Feste Formen

slots.py, SHAPES, _owner()

Eine Form gehört einem Namen, wenn darin genau ein Name vorkommt und alle übrigen Zellen Joker sind. Gefundene Muster werden nach Wert aufsteigend sortiert, damit die Auflösung von klein nach groß eskaliert.

Wertung: Faktoren und Pleite

slots.py, play_spin()

pleite  = (#Nieten ≥ 3)                → keine Muster
faktor  = min(∏ Faktorzellen, 20),  nur wenn mindestens ein Muster existiert
punkte[name] = Σ musterwert(name) · faktor

Sensations-Stufe und Tease

slots.py, tier_of(), tease()

Eine Stufe von 0 bis 4 steuert Licht, Ton, Wackeln und Banner:

4  wenn Volles Haus  oder Punkte ≥ 60
3  wenn bestes Muster ≥ 10  oder Punkte ≥ 24
2  wenn bestes Muster ≥ 3   oder Punkte ≥ 10
1  sonst (Treffer)      0  ohne Punkte

Tease: Steht in den Spalten 2–4 einer Reihe schon dreimal derselbe Name, stoppt die letzte Walze 2.300 ms später und läuft dabei sichtbar langsamer (siehe Walzen-Scroll).

Monte-Carlo-Kalibrierung der Quote

slots.py, quote()

An großen Tischen trifft ein einzelner Name seltener. Damit eine Wette trotzdem im Mittel 96 % zurückbringt, wird die Quote für jede Tischgröße simuliert:

rng   = Random(7919 · n)                  fester Seed je Tischgröße
E     = Σ punkte über 2.400 Spins / 2.400 / n
quote = 0,96 / E                          (RTP)
auszahlung = round(Σ einsatz[name] · punkte[name] · quote)

Kniff:Wegen des festen Seeds ergibt die gleiche Tischgröße auf jedem Rechner dieselbe Quote. lru_cache speichert sie. Ändert sich eine Wahrscheinlichkeit im Code, passt sich die Quote automatisch an.

Wetten als atomarer Austausch

draws.py, wager()

Ein Spieler schickt immer alle seine Einsätze auf einmal. Der Server rechnet mit dem Gesamtguthaben inklusive der schon gesetzten Chips:

verfügbar = chips + Σ bisherige einsätze
prüfe Σ neue einsätze ≤ verfügbar
alte einsätze löschen, neue einfügen, chips = verfügbar − Σ neu     (eine Transaktion)

Entfernt der Host einen Namen oder wechselt er den Modus, werden die betroffenen Einsätze zurückerstattet. Es gibt keinen Nachschuss: Wer bei 0 Chips steht, setzt aus, bis der Host die Bank zurücksetzt. Nachdrehen bei Gleichstand zahlt keine Einsätze aus, es entscheidet nur über die Punkte.

Unterstützer pro Name

app.py, public()

Neben jedem Namen zeigt die App, wie viele Leute auf ihn tippen oder setzen und wie viele Chips darauf liegen:

für jeden Tipp auf name:           unterstützer[name] += 1
für jeden Einsatz (wetter → name): unterstützer[name] += 1
                                   chips_darauf[name] += einsatz

Die Zählung läuft auf dem zurückgerechneten Stand (siehe Verzögerte Sichtbarkeit). Während die Walzen laufen, sieht man also noch die Einsätze vor der Abrechnung.

Session-Finale ohne Unentschieden

slots.py, play_round()

Eine Session hat 1, 3, 5 oder 7 Runden. Gezogen ist, wer über alle Runden die meisten Punkte hat. In der letzten Runde:

wiederhole Spin:
    genau ein Führender        → fertig
    Gleichstand / niemand vorn → „Nochmal!“
    nach 5 Spins               → das Los entscheidet unter den Führenden (+1 Punkt)

Weil jeder Name dieselbe Punkteverteilung hat, ist die Gewinnchance für alle gleich. test_slots_fair prüft das statistisch.

Symbolvergabe: 64 eindeutige Kombinationen

slots.py, skin_of(), assign_skins()

skin(k) = ( SYMBOL[k mod 8],  (BASISFARBE[k mod 8] + ⌊k / 8⌋) mod 8 )

Jede Runde durch alle 8 Bilder verschiebt die Farbe um eins. Die ersten 64 Kombinationen sind deshalb paarweise verschieden. Gespeicherte Kombinationen aus einer Gruppe werden zuerst vergeben, solange sie eindeutig sind. So behalten Stammspieler ihr Symbol.

Leerlauf-Raster mit teilerfremder Schrittweite

stages/slots.js, idleGrid()

Vor dem ersten Spin soll jeder sein Symbol sehen, und Nachbarn sollen sich unterscheiden:

step = erstes k ∈ [7, 5, 4, 3, 2, 1] mit ggT(k, n) = 1
zelle(c, r) = namen[ (r · 5 + c) · step  mod n ]

Weil step teilerfremd zu n ist, ist die Abbildung eine Permutation. Bei höchstens 15 Namen kommt jeder vor, und waagerechte Nachbarn sind nie gleich.

Zeit & Synchronisation

Fernseher und Handys zeigen dasselbe Bild, ohne Video-Stream. Möglich wird das durch eine gemeinsame Uhr und Zeitpläne, die der Server vorab festlegt.

Uhrabgleich mit Maximum-Filter

core.js, syncClock()

sample = server_ms − Date.now()
offset = sample                                    (erste Probe)
offset = max(sample, 0,8 · offset + 0,2 · sample)  (danach)
serverNow() = Date.now() + offset

Kniff:Netzwerkverzögerung macht eine Probe immer nur kleiner, weil die Serverzeit veraltet ankommt. Das Maximum hält die Probe mit der geringsten Verzögerung fest. Die Glättung lässt den Wert langsam nachgeben, falls eine Uhr driftet.

Ereignisgesteuerte Wakeup-Planung

app.py, schedule(), draws.py, wakeups()

Kein Polling: wakeups() liefert alle künftigen Zeitpunkte, an denen sich der Zustand ändert, also locks_at, calls_at und ends_at aller Runden. Ein einziger threading.Timer pro Tisch schläft bis zum frühesten davon (+80 ms Puffer), sendet dann den Zustand und plant sich neu.

Als Sicherheitsnetz ruft jede Zustandsberechnung zusätzlich settle() auf. Da es idempotent ist, wird ein verpasster Timer, etwa nach einem Neustart, beim nächsten Zugriff nachgeholt.

Verkettung der Slot-Runden

draws.py, _settle_slots()

Eine Slot-Session besteht aus mehreren Runden, deren Zeitpunkte erst feststehen, wenn die vorige Runde gedreht ist. Jede Runde wird bei ihrem locks_at gedreht, und dabei entsteht sofort die nächste:

ende          = started_at + dauer(zeitplan)
nächste Runde:
  calls_at    = ende                        Einsätze öffnen
  locks_at    = ende + 14.000 ms            (0, wenn kein Handy mitspielt)
  started_at  = locks_at + 1.700 ms
session.ends_at = jetzt + 6 h               Platzhalter bis zur letzten Runde

Das Drehen läuft in einer Schleife: Sind nach einem Neustart mehrere Runden fällig, werden alle nacheinander nachgeholt. Die Wakeup-Planung ignoriert Zeitpunkte, die mehr als 3 Stunden entfernt sind, damit der Platzhalter keinen Timer auslöst.

Der Regie-Zeitplan

slots.py, timeline()

Der Server rechnet jeden Spin vorab auf die Millisekunde durch und schreibt die Zeitpunkte in das Ergebnis:

stopp[c]   = 450 + 1.850 + 430 · c        (+2.300 auf der letzten Walze bei Tease)
nach Stopp : 900 Stille
Glück      : 720 je Umwandlung
Muster k   : min(1.500, 850 · 1,2^k)       jedes weitere Muster lässt länger warten
Faktor k   : 1.300 + 350 · k
Hochzählen : 1.500 + 650 · stufe  (+1.600 ab Stufe 3)
Pleite 2.700 · leer 1.900 · „Nochmal“ 2.100 · Los 3.300

Die Abstände wachsen geometrisch, und so steigt die Spannung von selbst. Zwischen zwei Runden liegen 14 s Pause für Rückblick und neue Einsätze.

Dauer einer Plinko-Ziehung

plinko.py, plinko_duration()

Der Server muss ends_at kennen, bevor die Kugel fällt. Er rechnet die Dauer aus denselben Konstanten wie die Animation:

dauer = 400 (Start) + 600 (Fall) + Σ_{k=0}^{rows−2} (520 − 14k) + 450 (Landung) + 400 (Halten)

rows = 8:   Σ = 7 · 520 − 14 · 21 = 3.346   →   dauer = 5.196 ms
rows = 16:  Σ = 15 · 520 − 14 · 105 = 6.330 →   dauer = 8.180 ms

Beim Glücksrad ist die Dauer fest (9,5 s), bei Slots ergibt sie sich aus dem Regie-Zeitplan.

Event-Replay mit stillem Aufholen

stages/slots.js, buildEvents(), replay()

Aus dem Zeitplan baut der Client eine sortierte Ereignisliste (Spin, Stopp, Umwandlung, Muster, Faktor, Hochzählen …) und arbeitet sie in jedem Frame ab:

solange events[i].at ≤ jetzt:
    apply(events[i], live = (jetzt − events[i].at < LIVE))
    i++

Wer die Seite mitten in einer Runde neu lädt, bekommt alle vergangenen Ereignisse still nachgespielt, ohne Ton und Effekte. Ab dem aktuellen Moment läuft alles live weiter. Das Prinzip entspricht Event Sourcing.

Event-Stream mit Backpressure und Backoff

handler.py, stream(), core.js, live()

  • Jeder Client hat eine eigene Queue mit höchstens 16 Einträgen. Ist sie voll, wird die Nachricht verworfen. Das ist unkritisch, weil jede Nachricht den vollständigen Zustand enthält.
  • Der Zustand wird einmal berechnet und nur pro Client um dessen eigene Daten ergänzt.
  • Ein Kommentar-Ping alle 15 s hält die Verbindung offen. Bei Abbruch verbindet der Client nach min(8 s, 0,8 s · 2^versuch) neu.

Animation & Kinematik

Keine Bühne speichert ihren Fortschritt. Jedes Bild ist eine Funktion von serverNow() − started_at.

Raddrehung: Kurve und ihre Ableitung

stages/wheel.js, angleAt()

θ(p)   = start + Δ · easeOutQuart(p)        easeOutQuart(p) = 1 − (1 − p)⁴
v(p)   = 4 · (1 − p)³                       genau die Ableitung
anlauf = −0,25 · sin(π · min(1, t/350))     kurz zurückziehen, dann losschnellen

Zeiger und Stift-Erkennung

wheel.js, frame()

Pro Name gibt es ⌈24/n⌉ Stifte. Ein Klick fällt, wenn sich der Stift unter dem Zeiger ändert:

unter = ⌊ ((−θ mod 2π) + 2π) mod 2π / stiftabstand ⌋
unter ≠ vorher  →  klick(lautstärke = 0,55 + 0,45 · (1 − p))
zunge += (stoß − zunge) · 0,45              exponentielle Glättung

Kamerazoom auf den Zeiger

wheel.js

smooth(a, b, x) = u² · (3 − 2u),   u = clamp((x − a)/(b − a))
zoom = 1 + 0,16 · smooth(0,6; 0,97; p)      um den Zeiger als Fixpunkt

Gegen Ende rückt die Kamera näher an den Zeiger. Nach dem Ergebnis zoomt sie über 900 ms wieder heraus.

Analytische Plinko-Bahn

stages/plinko.js, ballAt()

Es gibt keine Physik-Engine. Jedes Teilstück zwischen zwei Stiften ist eine geschlossene Formel:

dauer(k) = 520 − 14 · k  ms                 jeder Hop kürzer → wirkt wie Beschleunigung
x(u) = x₀ + (x₁ − x₀) · (1 − (1 − u)^1,7)
y(u) = y₀ + (y₁ − y₀) · u² − 0,35 · dy · sin(πu) · (1 − u)     Fall plus Hüpfer

Server und Client verwenden dieselben Konstanten, damit ends_at exakt zur Landung passt.

Geometrie des Plinko-Bretts

stages/plinko.js, layout()

Das Brett füllt jede Bildschirmgröße und bleibt dabei lesbar. Zuerst wird entschieden, ob die Namen waagerecht in die Fächer passen:

dxW   = 0,9 · breite / spalten
fH    = min(dxW · per · 0,2;  26 px)
flach = fH ≥ 13  ∧  längster Name ≤ 0,84 · fachbreite
binH  = flach ? 2,8 · fH : min(0,3 · höhe;  max(3,2 · dxW;  90))

dx    = min(dxW;  (0,9 · höhe − binH) / (1,4 + (rows − 1) · 0,9 + 0,9))
dy    = 0,9 · dx                     Reihenabstand
pegR  = clamp(0,08 · dx;  2,5;  9)    ballR = min(0,21 · dx;  20)

Passen die Namen nicht waagerecht, werden sie um 90° gedreht und senkrecht in die Fächer gesetzt.

Walzen-Scroll

stages/slots.js, animateReels()

pos[c] += dt · zelle · 0,028      (Tease: 0,011 – man sieht die Namen vorbeiziehen)
y = pos[c] mod (zelle · 1,08 · 9)             endloser Streifen aus 9 Füllzellen
ausholen: y = −0,12 · zelle · sin(π · (1 + t/450))

Die Füllzellen entstehen aus Zahlenfolgen wie (c·31 + k·17 + i·7) mod 23. Jede Walze sieht anders aus, aber auf allen Geräten gleich.

Größe des Slot-Automaten

stages/slots.js, layout()

zelle = max(28;  min(0,94 · breite / 5,9;  0,95 · höhe / 5,3;  170)) px

Der Automat ist etwa 5,9 Zellen breit (5 Walzen plus Rahmen) und mit Laufschrift und Zähler 5,3 Zellen hoch. Die Zellgröße wird als CSS-Variable gesetzt, alle anderen Maße leiten sich daraus ab.

Schriftgröße im Glücksrad

stage.js, labelFont()

Die Namen stehen radial in den Segmenten. Ihre Größe richtet sich nach der Bogenlänge, die das Segment auf Höhe des Textes hat:

bogen = segmentwinkel · r_text
cap   = R · (0,12 bei n ≤ 3 · 0,10 bei n ≤ 6 · 0,08 bei n ≤ 12 · sonst 0,064)
größe = max(8 px;  min(cap;  0,6 · bogen))

Text in Felder einpassen

stage.js, fitLabel()

f = max(0,6 · soll, 8 px, soll · platz / breite)      erst proportional verkleinern
danach zeichenweise kürzen, bis „text…“ passt

Bei Plinko entscheidet die Messung außerdem, ob die Namen waagerecht oder senkrecht in den Fächern stehen.

Hochzählen von Punkten und Chips

fx.js, countTo()

wert(u) = von + (bis − von) · (1 − (1 − u)³)        u = vergangene Zeit / Dauer
schritt = ⌊18 · u⌋   → bei jedem neuen Schritt ein Ton

Die Zahl läuft schnell an und bremst am Ende ab. Weil die Töne an den 18 Zeitschritten hängen und nicht am Zahlenwert, kommen sie gleichmäßig, egal ob von 0 auf 12 oder auf 12.000 gezählt wird. Die Dauer wächst mit der Sensations-Stufe.

Klangsynthese

Wie die einzelnen Klänge entstehen. Es gibt keine einzige Audiodatei: Alles wird live mit der Web-Audio-API erzeugt oder einmal Sample für Sample berechnet und dann nur noch abgespielt.

Bandbegrenzte Pulswellen

audio.js, pulse()

Pulswellen mit 12,5 / 25 / 50 % Tastgrad wie bei alten Konsolen, als Fourier-Reihe mit 40 Obertönen:

a_k = 2/(kπ) · sin(kπ · tastgrad) · σ_k
σ_k = sin(x)/x,   x = πk/41                 Lanczos-Gewichtung

Warum:Eine abgeschnittene Fourier-Reihe schwingt an den Kanten über (Gibbs-Phänomen). Das klingt schrill. Das σ-Fenster dämpft die hohen Obertöne weich ab.

4-Bit-Dreieck per DFT

audio.js, tri4()

Das Original-Dreieck des Chips hat nur 16 Stufen. Eine Treppe aus 32 Werten wird per diskreter Fourier-Transformation in 24 Obertöne zerlegt und als PeriodicWave abgespielt. Die typische Körnigkeit im Bass bleibt erhalten.

re_k = (2/32) · Σ v_i · cos(2πki/32),   im_k = (2/32) · Σ v_i · sin(2πki/32)

Rauschen aus einem 15-Bit-LFSR

audio.js, lfsr()

bit = (reg ⊕ (reg >> tap)) & 1          tap = 1 (lang) oder 6 (kurz, metallisch)
reg = (reg >> 1) | (bit << 14)
sample = reg & 1 ? +0,7 : −0,7          jeder Wert 4 Samples lang

Die lange Folge (32.767 Schritte) klingt wie Zischen, die kurze Folge tonal-metallisch. Daraus entstehen Snare, Hi-Hat und Wirbel.

Hüllkurven in 1/60-Sekunden-Schritten

audio.js, note(), _volume()

pegel(i)    = vol · (1 − i/frames)^decay,  gesetzt bei t + i/60
frequenz(i) = f · 2^((arp[i] + sweep · i + vibrato(i)) / 12)
vibrato(i)  = vib · sin(0,85 · (i − vibAt))   erst ab Frame vibAt
jede Stufe per setTargetAtTime(τ = 2,5 ms)    ohne Knacksen

Schlagzeug entsteht aus denselben Bausteinen. Die Kick ist ein Dreieck, das bei 170 Hz beginnt und pro Frame um 4,5 Halbtöne fällt, plus ein Rauschstoß. Die Snare ist 7 Frames Rauschen mit einem kurzen Puls bei 230 Hz, der um 3 Halbtöne pro Frame fällt.

Lautstärke und Tonhöhe springen wie früher im Takt der Bildwiederholung. Der kleine Glättungswert verhindert Klicks an den Stufen.

Weiche Stimmen für die Slot-Musik

audio.js, tone() bell() keys() pad(), slot-sfx.js, strings() strum()

Die Slots klingen nicht nach Konsole, sondern warm. Die Stimmen sind einfache additive Synthese mit Verstimmung:

StimmeAufbau
Tonlinearer Anschlag in a, exponentielles Ausklingen mit Zeitkonstante d, optional ein Gleiten von oben in höchstens 120 ms
GlockeGrundton + Oktave (0,28) + kurzer Glanz bei 4,2 · f (0,08, 50 ms)
E-PianoDreieck, abwechselnd ±4 Cent verstimmt, dazu eine leise Oktave
Flächezwei Sägezähne je Ton, ±7 Cent, gegenläufig im Stereobild, Tiefpass
Streicherdrei Sägezähne je Ton bei −11, +1 und +12 Cent, ein LFO mit 5,2 Hz moduliert alle um ±7 Cent
pegel_streicher = vol / √(3 · töne)       pegel_zupfen = 1,6 · vol / √(töne)

Die Wurzel sorgt dafür, dass ein Akkord mit sechs Tönen nicht doppelt so laut ist wie einer mit drei: Unkorrelierte Stimmen addieren sich in der Leistung, nicht in der Amplitude. Beim Zupfen erklingen die Töne 7 ms versetzt von unten nach oben und werden über das Stereobild verteilt.

Gezupfte Saiten nach Karplus-Strong

slot-sfx.js, pluckBuf()

N = round(sr / f − 0,5)                 Länge der Verzögerungsleitung
q = tiefpass(rauschen)                  weicher Anschlag „mit dem Daumen“
y[i] = q[k];   q[k] = g · ½ · (q[k] + q[k+1])
g = 10^(−3 / (T60 · sr / (N + 0,5)))     Abklingen um 60 dB in T60
rate = f · (N + 0,5) / sr               Stimmkorrektur über die Abspielrate

Die Saiten werden im Leerlauf nach und nach vorberechnet (3 Töne alle 40 ms), damit die Auszahlungsmusik später nie hakt.

Modalsynthese mit Resonatorbank

slot-real.js, bank(), dense()

Ein Körper schwingt in vielen Moden. Jede Mode ist ein Zwei-Pol-IIR-Resonator:

r = e^(−1/(τ · sr)),  ω = 2πf/sr
y[n] = 2r·cos ω · y[n−1] − r² · y[n−2] + g·sin ω · x[n]

dense(n, lo, hi):  f = lo · (hi/lo)^U,   g = (f/lo)^(−tilt) · U(0,3; 1)

Die Frequenzen sind logarithmisch zufällig verteilt, eine Spektralneigung macht hohe Moden leiser. Angeregt wird mit gefiltertem Rauschen oder einem Halbsinus-Impuls. Ein Walzen-Stopp besteht aus sechs Schichten: Gewicht (48–100 Hz), Holz, Klopfen, Sperrklinke, Metallring und Nachfedern. Die Ratsche hat 16 Varianten aus je etwa 40 Resonanzen.

Marimba und dumpfer Schlag als Sinus-Summe

slot-sfx.js, modal(), mallet(), THUD

Eine zweite, einfachere Form der Modalsynthese: Statt Filter anzuregen, werden abklingende Sinusse direkt addiert, plus ein kurzer Rauschklick als Anschlag:

s(t) = klick · e^(−t/τ_k) · rauschen  +  Σ a_i · e^(−t/τ_i) · sin(2π f_i t)

marimba(f):  [f; 0,30 s; 1]  [3,93 f; 0,05; 0,32]  [9,2 f; 0,012; 0,1]  [2 f; 0,12; 0,06]
schlag:      56, 88, 150, 400, 900 Hz mit 100 … 5 ms Abklingzeit

Die Teiltöne 3,93 und 9,2 entsprechen ungefähr denen eines echten Klangstabs. Für das Rauschen nutzt die Funktion einen kleinen Zufallsgenerator mit festem Startwert (x = (9301 · x + 49297) mod 233280), damit jeder Ton bei jedem Anschlag identisch klingt. Jede Note wird einmal berechnet und zwischengespeichert, die Saiten und Marimbatöne werden im Leerlauf vorbereitet.

Glocke mit unharmonischen Teiltönen

slot-real.js, bellArr()

f = 1.180 Hz · [1 ; 2,76 ; 5,40 ; 8,93 ; 13,34]
τ = [0,90 ; 0,45 ; 0,25 ; 0,12 ; 0,07] s

Echte Glocken haben keine ganzzahligen Obertöne. Genau diese Verhältnisse machen den Klang metallisch statt orgelhaft.

Hall-Impulsantworten und Rauschfarben

audio.js, room(), slot-real.js, ir(), loopNoise()

raum:  y += 0,35 · (rauschen − y);   h[i] = y · e^(−5t)          gefiltert, abklingend
braun: b = (b + 0,02 · x) / 1,02                                 leckender Integrator

Die Impulsantworten werden per ConvolverNode gefaltet: ein kurzer Gehäuseklang (0,3 s) für die Mechanik und ein Saal (2,4 s) für den Jackpot.

Rattern der Walzen und Münzregen

slot-real.js, rateOf(), pump(), coinRain()

Jede laufende Walze erzeugt Rastgeräusche, deren Takt einer kleinen Mechanik folgt:

anlauf:  rate = 6 + 12 · min(1; (t − start) / 0,35 s)          6 → 18 Zähne/s
auslauf: rate = 18 − 13 · min(1; (t − langsam_ab) / 2,3 s)^0,7  nur Spannungs-Walze
nächster zahn += (1 / rate) · U(0,88; 1,12)                    ±12 % Unruhe

Jeder Zahn wählt eine von 16 vorberechneten Varianten, mit zufälliger Lautstärke und ±5 % Tonhöhe. Geplant wird alle 25 ms für die nächsten 120 ms. Darunter liegt ein Schnurren aus gefiltertem Rauschen, das ein LFO mit 15 Hz flattern lässt wie die vorbeiziehenden Bänder.

Beim Jackpot fallen 45 Münzen in 2,2 s. 70 % ihrer Zeitpunkte folgen u^1,6 und häufen sich deshalb am Anfang, wie bei einem echten Schwall. Die Lautstärke fällt dabei linear auf die Hälfte.

Klangkanäle ohne Überlappung

slot-sfx.js, chan(), audio.js, roll()

Jede Klangart hat einen eigenen Kanal (Ergebnis, Feld, Zählen, Gewinn). Ein neuer Klang auf demselben Kanal blendet den vorigen mit einer Zeitkonstante von 70 ms aus, statt sich darüberzulegen. Folgen viele Ereignisse schnell aufeinander, bleibt der Klang so sauber.

Das Rollen der Plinko-Kugel ist eine Rauschschleife, deren Abspielrate und Lautstärke der Geschwindigkeit folgen: rate = 0,08 + 0,3 · v, pegel = 0,008 + 0,03 · v.

Musik

Die Musik ist komponiert und reagiert trotzdem auf das Spiel. Alles steht in a-Moll, jedes Ereignis spielt Töne des Akkords, der gerade klingt, und jede Spannung löst sich an einem vorher berechneten Zeitpunkt auf.

Tonmaterial: a-Moll und Pentatonik

audio.js

Alle Töne sind MIDI-Nummern und werden gleichstufig umgerechnet:

f(m) = 440 Hz · 2^((m − 69) / 12)          m = 69 → A4,  m = 57 → A3

PENTA       = [0, 2, 4, 7, 9, 12, 14, 16, 19, 21, 24, 26, 28]   Dur-Pentatonik, 2½ Oktaven
MINOR_PENTA = [0, 3, 5, 7, 10]                                  Moll-Pentatonik

Die gesamte Musik steht in a-Moll. Für schnelle Effektklänge (Chips, Stifte, Zählen) dient die Pentatonik: Sie hat keine Halbtonschritte, also klingt jede Kombination ihrer Töne konsonant, auch wenn viele gleichzeitig erklingen.

Look-ahead-Scheduler und Serverzeit → Audiozeit

audio.js, at(), slot-sfx.js, pump()

Alle Musik und alle Klänge laufen über diesen Mechanismus:

alle 25 ms:
    solange nächster_schritt < jetzt + 150 ms:
        spiele schritt(nächster_schritt + swing)      swing = 16tel · 0,16 auf Offbeats
        nächster_schritt += 16tel
audio_t(server_ms) = ctx.currentTime + (server_ms − serverNow()) / 1000

raster auf ziel legen (Countdown):
    k = ⌊(ziel − jetzt) / 16tel⌋;   erster_schritt = ziel − k · 16tel
nächste achtel(t): ab dem Raster in Achteln vorrücken, bis ≥ t

Für den Countdown wird das Raster rückwärts vom Ziel aus angelegt, sodass der letzte Schritt exakt auf „Keine Wetten mehr“ fällt. Treffer, Rundenende und Schlussakkorde werden auf die nächste Achtel gelegt und sitzen damit im Takt. Ist der Tab im Hintergrund, holt der Scheduler verpasste Schritte nicht nach, sondern setzt neu an.

Warum:JavaScript-Timer sind ungenau, die Audio-Uhr nicht. Töne werden im Voraus auf der Audio-Zeitachse geplant und sitzen deshalb sample-genau auf den Ereignissen, die der Server vorgegeben hat.

Das Lobby-Thema

audio.js, SCENES.lobby

Ein 16-taktiges Thema in a-Moll bei 112 bpm mit 16 % Swing. Teil A beruht auf der absteigenden Folge Am – G – F – E7 (der „andalusischen Kadenz“), Teil B weicht in die Subdominante aus:

A:  Am  G   F   E7 │ Am  G   F→E7  Am
B:  Dm  Am  Dm  E7 │ F   G   Am    E7
  • Bass (Dreieck) auf den Sechzehnteln 0, 3, 6, 8, 11 und 14: Grundton, Oktave, Quinte, Grundton, Oktave, dann ein Halbton zum nächsten Grundton hin. Dieser chromatische Leitton zieht jeden Takt in den nächsten.
  • Melodie (25 %-Puls) mit leichtem Vibrato ab Frame 12. Ein Echo drei Sechzehntel später spielt sie leiser auf 12,5 %-Puls und nach rechts versetzt.
  • Schlagzeug: Kick auf 1 und auf der „und“ der 3 (Sechzehntel 10), Snare auf 2 und 4, Hi-Hat auf Achteln mit Betonung der Viertel. Vor jeder Wiederholung (Takt 8 und 16) ein ansteigender Snare-Wirbel.
  • Glitzer: In den Takten 13–15 laufen sehr leise Akkordtöne drei Oktaven über dem Grundton.

Die ersten vier Takte des Themas kehren später in der Slot-Musik wieder.

Countdown: ein Halbton pro Sekunde

audio.js, SCENES.calls

Während der letzten Einsätze läuft ein Groove bei 120 bpm. Eine Sechzehntel ist dann genau 125 ms lang, acht Sechzehntel sind eine Sekunde. Das macht die Rechnung einfach:

übrig     = verbleibende Sechzehntel bis „Keine Wetten mehr“
anstieg   = ⌊(gesamt − übrig) / 8⌋          Halbtöne, einer pro Sekunde
bass      = 33 + anstieg (+12 im Wechsel)
ostinato  = 69 + anstieg + [0, 7, 12, 7]   Grundton, Quinte, Oktave, Quinte
sekunde   = Ton 81, die letzten drei: 84, 86, 88, lauter und länger

In den letzten zwei Sekunden kommt ein Rauschwirbel dazu, der bis zum Schluss anschwillt. Auf Handys, die keine Musik spielen, ersetzt ein Holzblock-Ticken den Countdown. Die letzten drei Sekunden sind dort Glocken auf E, G und C.

Musik, die dem Rad folgt

audio.js, SCENES.spin, tick()

Während das Rad dreht, bestimmt sein Fortschritt L (0 = schnell, 1 = steht), was die Musik spielt. Sie läuft bei 150 bpm:

BereichMusik
L < 0,45treibend: Kick, Snare, Bass in Oktaven, Arpeggio. Alle zwei Takte Wechsel zwischen a-Moll und F-Dur (Grundton −4 Halbtöne).
0,45 – 0,8Alles steigt: Bass und Arpeggio rücken alle 8 Sechzehntel einen Halbton höher (höchstens 8), darüber eine lang gehaltene „Sirene“ mit Vibrato.
0,8 – 0,995nur noch ein Herzschlag (zwei Kicks pro halben Takt) und ein leiser hoher Wechselton
≥ 0,995Stille vor dem Ergebnis

Die Klicks am Zeiger durchlaufen bei schnellem Rad reihum die Moll-Pentatonik (81 + [0, 3, 5, 7, 10]). Ab L = 0,8 steigen sie stattdessen chromatisch, Halbton für Halbton (69 + k, bis zu zwei Oktaven), und werden lauter. Klicks, die weniger als 22 ms auseinanderliegen, werden verworfen.

Tonleitern für Chips, Stifte und Zählen

audio.js, chip() ping() score() coins()

chip      79 + PENTA[combo], 2 Frames später +5 (Quarte)
          combo +1 je Chip, zurück auf 0 nach 0,8 s Pause
ping      72 + PENTA[reihe mod 13]   Echo nach 120 ms auf der anderen Seite
zählen    76 + PENTA[schritt]
münzen    91 + PENTA[0 … 5],  zeitpunkt = U^1,5 · streuung

Wer schnell hintereinander Chips setzt, hört eine aufsteigende Tonleiter. Die Plinko-Kugel spielt bei jeder Reihe den nächsten Pentatonik-Ton und steigt hörbar, während sie fällt.

Kadenzen der Ziehung

audio.js, slam() reveal() lose() kaching() powerOn()

Die Schlüsselmomente sind kleine Schlusswendungen, harmonisch geplant:

  • „Keine Wetten mehr“: Eine Fläche auf A – E – C – H, also a-Moll mit hinzugefügter None, und ein tiefes A. Darüber fallen drei Glocken E – C – A, der Akkord rückwärts gebrochen. Danach ist es still, bis das Rad startet.
  • Ergebnis: Nach der ganzen Musik in Moll endet die Ziehung in A-Dur, das Prinzip der „picardischen Terz“. Ein Arpeggio A – Cis – E – A, dann E, A und ein langes Cis mit Vibrato. Der Bass spielt A – E – A, also Tonika – Dominante – Tonika.
  • Gewinn eingestrichen: E → A (Quarte aufwärts), bei großem Gewinn zusätzlich ein schnelles A-Dur-Arpeggio (A – Cis – E – A – Cis) und Münzen.
  • Die Bank gewinnt: Eine „traurige Posaune“: E – Es – D – Des chromatisch abwärts, der letzte Ton lang mit Vibrato. Der Bass geht parallel A – As – G – Ges.
  • Einschalten: Rauschen, dessen Tonhöhe pro Frame um den Faktor 1,17 steigt, dann ein Sprung über A – E – A – E – A – E (abwechselnd Quinte und Quarte) und ein Münzklang.

Slot-Musik als durchgehendes Stück

slot-sfx.js, Bed, betting() lock() tease()

Eine Slot-Session ist ein einziges Musikstück, eine Variante des Lobby-Themas: gleiches Tempo (112 bpm), gleicher Swing, gleiche Akkordfolge Am – G – F – E. Es gibt keine Pausen, nur die Dichte ändert sich.

  • Nahtloser Übergang: Läuft gerade die Lobby-Musik, übernimmt die Slot-Musik deren Raster: gleiche Sechzehntel, gleicher Takt, gleicher Akkord. Die Lobby wird über 1,6 s ausgeblendet.
  • Letzte Einsätze: Drei, zwei und eine Sekunde vor Schluss erklingen Glocken auf E, Gis und H, der Dur-Dreiklang der Dominante. „Keine Wetten mehr“ löst ihn nach a-Moll auf.
  • Nach dem Lock: zwei Holzschläge, dann ein E-Dur-Akkord und Streicher auf E7. Die Dominante verlangt nach Fortsetzung, und die kommt mit dem Hebel.
  • Tease: Die Harmonie bleibt auf E stehen (Orgelpunkt), der Bass spielt nur noch Viertel, dazu ein Herzschlag aus zwei tiefen Schlägen, die Hi-Hats werden mit jedem Schlag lauter, eine Glocke klettert durch die Akkordtöne. Die Spannung löst sich erst mit dem Ergebnis.

Jeder Modus hat einen eigenen Tiefpass und Pegel. Während die Walzen laufen, ist die Musik leise (Pegel 0,22, Filter 1.500 Hz), damit die Mechanik vorn steht. In der Pause zwischen den Runden ist sie offen und warm (0,55, 2.800 Hz).

Energie-Modell der Slot-Musik

slot-sfx.js, Bed

Ein einzelner Wert E ∈ [0, 1] bestimmt, wie dicht die Musik ist:

ereignis:   E = min(max, E + Δ)                 jede Walze, jeder Treffer legt nach
countdown:  E = max(E, 0,35 + 0,6 · u)          baut bis „Keine Wetten mehr“ auf
sonst:      E = max(boden, E − 0,0035)          sinkt pro 16tel langsam ab

Die Energie entscheidet, welche Instrumente spielen:

EnergieArrangement
immerFläche zu jedem Takt (Pegel und Filter wachsen mit E), Sechzehntel-Hats, Bass im Lobby-Muster mit chromatischem Übergang, Sägezahn mit Filter 500 + 700·E Hz plus Suboktave
außer beim DrehenAkkordstöße auf der „und“ (Sechzehntel 6 und 14)
E > 0,3Clap auf 2 und 4
E > 0,45Kick auf jedem Viertel statt nur auf 1 und 3
E > 0,5offene Hat auf dem Offbeat, Arpeggio in Achteln (Muster 0-1-2-3-4-3-2-1 durch die Akkordtöne)
E > 0,65Das Lobby-Thema kommt obenauf, als Glocke und gefilterte Rechteckwelle.
E > 0,8Arpeggio in Sechzehnteln

Jeder Modus hat einen eigenen Boden, Tiefpass und Pegel: Einsätze, Lock, Spin, Tease, Zählen, Pause. Pleite oder ein leerer Spin lassen die Musik kurz abtauchen (Pegel und Filter fallen, kommen exponentiell zurück), statt sie abzuschneiden. Beim Hochzählen steigen geplante Akkordstöße Stufe für Stufe und landen genau mit dem Zählerstand auf a-Moll. Dort setzt das Raster neu an (landAt).

Jeder Treffer spielt den nächsten Akkordton

slot-sfx.js, Bed.tone(), pattern() multiplier()

Alles, was auf dem Automaten passiert, ist Teil der Musik. Ereignisse spielen Töne des Akkords, der gerade klingt, und zählen dabei aufwärts:

töne = Akkordtöne, jeweils um Oktaven über basis gehoben, sortiert
ton(k) = töne[k mod 5] + 12 · ⌊k / 5⌋

umkehrung(akkord, n) = n-mal den tiefsten Ton eine Oktave höher legen
  • Muster k: Glocke auf ton(k + 1) plus Oktave darunter, dazu der Akkord gezupft in der Umkehrung k mod 3. Ab Musterwert 5 laufen drei weitere Glocken nach oben.
  • Faktor k: ein kurzer Luftzug, dann ein voller Schlag auf F, G, E oder Am (reihum) in Umkehrung k. Jeder weitere Faktor klingt höher.
  • Glücks-Umwandlung k und Feld-Anzählen: Glocke bzw. Marimba auf ton(k + 2) bzw. ton(feld + schritt).

Weil die Töne immer aus dem laufenden Akkord kommen, entsteht keine Dissonanz, egal wie viele Treffer zusammenkommen.

Abrechnung: eine Akkordleiter mit Stimmführung

slot-sfx.js, payoff(), fanfare()

Beim Hochzählen der Punkte erklingt eine Akkordfolge, die genau mit dem Zählerstand auf a-Moll landet. Zuerst wird die Zahl der Akkorde aus der Dauer bestimmt und die Folge so gedreht, dass sie immer auf der Dominante E endet:

n       = max(3; round(dauer / achtel))
akkord k = [Am, F, G, E][(k + 4 − n mod 4) mod 4]        letzter immer E
u       = k / (n − 1)
umkehrung = min(2; ⌊3u⌋)       streicher: pegel 0,04 + 0,08u,  filter 1.300 + 1.600u Hz

Die Marimba-Oberstimme wird rückwärts gebaut, vom Zielton aus:

ton[n−1] = 80 (Gis5, Leitton zu A)
ton[k]   = höchster Akkordton von akkord k, der unter ton[k+1] liegt
           und höchstens eine große Terz (4 Halbtöne) entfernt ist
           (gibt es keinen, der nächste Akkordton darunter)

So steigt die Melodie in kleinen Schritten zum Gis. Die Landung auf a-Moll wählt dann die Lage, die zur letzten Umkehrung passt, damit sich alle Stimmen nur um einen Schritt bewegen: Gis geht nach A. Je nach Sensations-Stufe kommen Schichten dazu (Oktave, volle Akkorde, Marimba-Lauf). Danach setzt der Groove einen Schlag später genau auf a-Moll neu ein.

Jackpot-Jingle, rückwärts getaktet

slot-real.js, jackpot()

Ab Stufe 4 schweigt die normale Musik, und ein eigener Automaten-Jingle übernimmt. Sein Tempo wird aus der Zieldauer berechnet:

spanne = max(1,4 s; ende − start)
n      = clamp(round(spanne / 0,4 s); 4; 8)   Schläge Anlauf  (≈ 150 bpm)
schlag = spanne / n,   shuffle = ⅔ · schlag    Triolen-Feeling
start  = ende − n · schlag
akkord k = [F, G, Am, E7][(k + 4 − n mod 4) mod 4]          letzter immer E7

Auf dem Schlag spielt der Bass, auf dem Shuffle-Nachschlag der Akkord. Eine Marimba spielt „ding-da“ auf zwei Akkordtönen, in den letzten vier Schlägen eine Oktave höher. Am Ziel: a-Moll, ein Riff A – E – G – A – C – A, zwei Glocken, der Münzregen und nach drei Schlägen ein voller Schlussakkord.

Pleite, Nochmal, Rundenende, Finale

slot-sfx.js

  • Zwei Nieten im Bild: tief E – H (reine Quinte), dann E – B (Tritonus). Die Dissonanz warnt, ohne laut zu sein.
  • Pleite: drei Marimbatöne chromatisch abwärts (E – Es – D), dann d-Moll. Die Musik fällt auf 20 % und Filter 400 Hz und kommt über 2,6 s zurück.
  • Kein Muster: E → C (große Terz abwärts), die Musik taucht auf 50 % ab.
  • Nochmal: ein Luftzug, dann E7. Die Dominante sagt „es geht weiter“.
  • Das Los: 26 Rauschschläge im Abstand von 50 ms, jeder lauter, dann eine Glocke auf A mit a-Moll.
  • Rundenende: E7 → Am, die Grundkadenz Dominante → Tonika, auf die nächste Achtel im Raster gelegt.
  • Finale: ein großes a-Moll mit hinzugefügter None (A – E – A – C – E – H – C), sechs Glocken aufwärts, dann blendet die Musik über 3 s aus.

Groove-Puls: Die Oberfläche atmet im Takt

audio.js, groove(), beatLoop()

Jeder Kick und jede Snare wird mit Zeit und Stärke protokolliert. Die Knöpfe pulsieren genau zu dem Schlag, der gerade hörbar ist. Dabei wird die Ausgabelatenz des Geräts abgezogen:

jetzt = ctx.currentTime − outputLatency
puls  = stärke · e^(−7 · (jetzt − t_schlag))

Infrastruktur

Das Programm verteilt sich als eine einzige Datei, und eine Datenbank, die jahrelang mitwachsen kann.

Einzeldatei mit eigenem Importer

tools/bundle.py

Code, Vorlagen, CSS/JS, Schriften und Migrationen werden als ZIP (Kompressionsstufe 9) gepackt, Base64-kodiert und in eine .py-Datei eingebettet. Beim Start hängt sich ein MetaPathFinder + Loader in sys.meta_path:

find_spec("auslosung.x")  → pfad im ZIP-Speicher suchen (.py oder /__init__.py)
exec_module(m)            → compile(quelle, "<bundle>/…") und exec
auslosung._bundle.FILES   → alle Nicht-Python-Dateien als {pfad: bytes}

Alle Einträge im ZIP haben den festen Zeitstempel 2020-01-01. Gleicher Code ergibt so immer eine Datei mit identischen Bytes.

Migrationen in PRAGMA user_version

db.py, migrate()

für jede datei NNNN_name.sql mit NNNN > user_version:
    PRAGMA foreign_keys = OFF
    BEGIN; <sql>; PRAGMA user_version = NNNN; COMMIT;
    fehler = PRAGMA foreign_key_check
    PRAGMA foreign_keys = ON;  fehler → abbrechen

Warum:SQLite kann Spalten nur begrenzt ändern. Tabellen werden deshalb kopiert und neu angelegt. Mit aktiven Fremdschlüsseln würde ON DELETE CASCADE dabei abhängige Zeilen löschen. Die nachträgliche Prüfung stellt sicher, dass trotzdem alles konsistent ist.

Verschachtelte Transaktionen

db.py, transaction()

tiefe 0:  BEGIN IMMEDIATE … COMMIT / ROLLBACK
tiefe n:  SAVEPOINT spN … RELEASE spN / ROLLBACK TO spN

Jeder Thread hat eine eigene Verbindung (threading.local), die Datenbank läuft im WAL-Modus. Schreibzugriffe laufen über ein RLock. IMMEDIATE holt die Schreibsperre sofort und vermeidet damit Deadlocks, wenn mehrere Transaktionen gleichzeitig vom Lesen zum Schreiben wechseln wollen.

Content-Hash-Caching

web/assets.py

version = sha1(alle pfade + inhalte)[:10]   → /static/…?v=version
etag    = sha1(datei)[:16]
mit ?v  → Cache-Control: max-age=1 Jahr, immutable
ohne ?v → no-cache + If-None-Match → 304

Pfadschutz für beide Fassungen

resources.py, _clean(), read()

rel = normpath(rel mit "/" statt "\").lstrip("/")
rel ∈ {"", ".", ".."} oder beginnt mit "../"  → abgelehnt
dateisystem: (ROOT / rel).resolve() muss unter ROOT liegen

Dieselbe Funktion liest aus dem Dateisystem oder aus dem Bundle-Speicher. Der Rest des Programms muss nicht wissen, in welcher Fassung er läuft.
